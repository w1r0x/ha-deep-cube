# ha-deep-cube

Неофициальная интеграция Home Assistant для кубика сна deep (deep.r, в перспективе deep.n). Работает локально по Bluetooth LE, без облака и аккаунта производителя. Репозиторий публичный: https://github.com/w1r0x/ha-deep-cube.

Перед началом работы прочитать `docs/protocol.md` — это единственный источник правды о протоколе.

## Структура

- `custom_components/deep_cube/` — код интеграции (домен `deep_cube`).
- `hacs.json`, `README.md` — в корне, для установки через HACS как пользовательского репозитория. `README.ru.md` — русский дубль README.
- `docs/protocol.md` — описание BLE-протокола. Обновлять при каждом новом факте о протоколе.
- `tools/` — отладочные скрипты для ПК на `bleak`: `deep_cube.py` (прототип управления), `gatt_dump.py`, `monitor.py`, `btsnoop_att.py`.
- `tests/` — тесты `pytest`: протокольный модуль и согласованность переводов. Запуск: `.venv/Scripts/python -m pytest`.
- `.github/workflows/validate.yml` — проверки на GitHub: тесты, hassfest, HACS.
- `changes/` — описания завершённых доработок.
- `.local/` — локальные данные вне Git: `cube_address` с адресом кубика для скриптов, `raw/` с сырыми логами.

## Правила работы с кубиком

- Сервис `f000ffc0-0451-4000-b000-000000000000` — обновление прошивки. Никогда не писать в его характеристики.
- Отправлять кубику только те команды и значения, что описаны в `docs/protocol.md`. Новые значения сначала наблюдать в обмене официального приложения (HCI-лог), потом использовать.
- Кубик принимает одно соединение. Интеграция подключается по требованию: команда или опрос, чтение статуса, отключение. Соединение не удерживать, чтобы приложение deep up оставалось рабочим.
- Ответ «принято» на команду старта не означает запуск. Результат проверять чтением статуса.
- Перед тестом с ПК убедиться, что приложение deep up на телефоне закрыто.

## Правила разработки интеграции

- Настройка только через config flow, с автообнаружением по Bluetooth (`bluetooth` в `manifest.json`). Никакого YAML.
- Bluetooth — только через стек Home Assistant: `homeassistant.components.bluetooth` для поиска устройства и `bleak-retry-connector` для соединения. Не создавать собственные сканеры и не обращаться к адаптерам напрямую: интеграция должна работать через ESPHome Bluetooth Proxy.
- Протокол (кодирование команд, разбор статуса) держать в отдельном модуле без зависимостей от Home Assistant, чтобы его можно было покрыть тестами и позже вынести в библиотеку.
- Опрос — через `DataUpdateCoordinator`. Весь ввод-вывод асинхронный, без блокирующих вызовов.
- У каждой сущности — стабильный `unique_id` на основе адреса устройства и `has_entity_name = True`.
- Тексты интерфейса — в `strings.json` и `translations/` (минимум `en` и `ru`). В коде строк для пользователя не держать. `translations/en.json` — копия `strings.json` (Home Assistant читает у пользовательских интеграций только `translations/`); совпадение и полноту переводов проверяют тесты.
- Модель deep.n обнаруживается и работает по протоколу deep.r, но не проверена. Сведения о ней собирать через issues и PR.
- Код — с аннотациями типов, в стиле ядра Home Assistant.
- Версию в `manifest.json` повышать при каждом изменении поведения.
- Тесты протокольного модуля — `pytest`, без реального устройства.

## Язык

- Вся документация репозитория — на английском: `README.md`, `docs/`, `changes/`, комментарии и docstring в коде и в `tools/`, сообщения скриптов, сообщения коммитов.
- `README.ru.md` — полный русский дубль `README.md`. Менять оба файла одновременно, чтобы они не расходились.
- Исключение: `AGENTS.md` (рабочие правила, на русском).
- Названия программ и пунктов приложения deep up приводить в оригинале с переводом в скобках: «Просто сон» (Just Sleep).
- Интерфейс интеграции переводится через `translations/`: `en` и `ru` обязательны, остальные языки добавляются отдельными файлами без правки кода.

## Проверка на реальном Home Assistant

- Установка для проверки — копирование `custom_components/deep_cube/` в `/config/custom_components/` и перезапуск Home Assistant.
- После установки проверить состояние записи интеграции и свежие логи.
- Сведения о конкретной установке Home Assistant (адреса, способы доступа, имена устройств) в репозиторий не записывать.

## Публичность и секреты

- Репозиторий публичный. Не коммитить: адрес и серийный номер кубика, сырые HCI-логи (`btsnoop_hci_*.log` содержат чужой трафик и ключи сопряжения), bug report телефона, APK приложения, токены и адреса домашней сети.
- В документации адрес кубика писать в виде `5C:01:3B:xx:xx:xx`.
- Перед коммитом просмотреть индекс на предмет перечисленного выше.
- В описаниях указывать, что интеграция неофициальная и не связана с производителем.

## Документирование завершённых доработок

- После полного завершения каждой доработки создать отдельный Markdown-файл с её описанием в каталоге `changes/`.
- Имя файла: `YYYY-MM-DD-short-name.md`, на английском. Несколько доработок в один день — разные понятные названия.
- В описании указать: задачу или исходную проблему, найденную причину (если это исправление), принятое решение и как оно реализовано, изменённые файлы, выполненные проверки и их результат, известные ограничения, порядок отката.
- Доработка считается завершённой только после создания или актуализации этого файла. В итоговом ответе пользователю давать ссылку на него.

## Работа с Git

- Работать в ветке `main`. Отдельные ветки не создавать, если пользователь явно не попросил.
- После каждой завершённой доработки обязательно делать коммит. Завершённой считается доработка, для которой выполнены проверки и создан или актуализирован файл в `changes/`.
- Один коммит — одна тема. Несвязанные изменения разносить по отдельным коммитам.
- В коммит включать всё, что относится к доработке: код, тесты, документацию, описание в `changes/`.
- Не оставлять незакоммиченные изменения по завершённой работе.
- `git push` публикует изменения для всех. Выполнять его только по явной просьбе пользователя.
